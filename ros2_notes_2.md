## 1. Workspace & Package Basics

A ROS 2 workspace (e.g. `~/bumperbot_ws`) has this structure:
```
bumperbot_ws/
├── src/        # source code — packages go here
├── build/      # generated by colcon build
├── install/    # generated by colcon build — what you "source"
└── log/        # build logs
```

Creating a new **Python** package:
```bash
cd ~/bumperbot_ws/src
ros2 pkg create --build-type ament_python <package_name>
```

Creating a new **C++/CMake** package (used for description/URDF packages too):
```bash
ros2 pkg create --build-type ament_cmake <package_name>
```

**Lesson learned:** `ros2 pkg create-- build-type` (no space, double dash) is invalid — the command is `create` then a separate `--build-type` flag.

## 2. Running Nodes with `ros2 run`

Syntax:
```bash
ros2 run <package_name> <executable_name>
```

Both arguments are required — running `ros2 run <package_name>` alone throws:
```
error: the following arguments are required: executable_name, argv
```

To discover what executables exist in a package:
```bash
ros2 pkg executables <package_name>
```

If nothing shows up, the executable was never registered in `setup.py`'s `entry_points`, or the workspace hasn't been rebuilt since it was added.

## 3. Python Package Structure (`setup.py`)

Every node needs an entry in `entry_points` to be runnable via `ros2 run`:

```python
entry_points={
    'console_scripts': [
        'simple_publisher = bumperbot_py_examples.simple_publisher:main',
        'simple_subscriber = bumperbot_py_examples.simple_subscriber:main',
        'simple_parameter = bumperbot_py_examples.simple_parameter:main',
    ],
},
```

**Format:** `<executable_name> = <package_name>.<module_name>:<function_name>`

**Lesson learned (important bug):** the module path here (`bumperbot_py_examples`) **must exactly match** the actual inner package folder name. A typo (e.g. `bumpebot_py_examples` vs `bumperbot_py_examples`) causes:
```
ModuleNotFoundError: No module named 'bumpebot_py_examples'
```
even though the executable itself was found — because the generated script tries to `import` a module that doesn't exist under that name.

**Lesson learned (unsaved files):** if `setup.py` shows an unsaved-changes dot (`●`) in the editor tab, `colcon build` will use the **old saved version on disk**, not what's visible in the editor. Always save (`Ctrl+S`) before building.

After any change to `setup.py`, always:
```bash
colcon build --packages-select <package_name>
source install/setup.bash
```

## 4. Writing a Simple Publisher

`simple_publisher.py`:
```python
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class SimplePublisher(Node):

    def __init__(self):
        super().__init__("simple_publisher")

        self.pub_ = self.create_publisher(String, "chatter", 10)

        self.counter_ = 0
        self.frequency_ = 1.0

        self.get_logger().info("Publishing at %d Hz" % self.frequency_)

        self.timer_ = self.create_timer(
            self.frequency_,
            self.timerCallback
        )

    def timerCallback(self):
        msg = String()
        msg.data = "Hello ROS 2 - counter: %d" % self.counter_

        self.pub_.publish(msg)
        self.counter_ += 1


def main():
    rclpy.init()
    simple_publisher = SimplePublisher()
    rclpy.spin(simple_publisher)
    simple_publisher.destroy_node()
    rclpy.shutdown()


if __name__ == "__main__":
    main()
```

**What it does:** creates a node that publishes a `std_msgs/String` message on the `/chatter` topic once per second (`create_timer`), incrementing a counter each time.

**Key concepts:**
- `create_publisher(MsgType, topic_name, queue_size)` sets up the publishing interface.
- `create_timer(period_seconds, callback)` fires `callback` repeatedly at a fixed interval.
- `rclpy.spin(node)` keeps the node alive and processing callbacks until shutdown (Ctrl+C).

Verify it's working in another terminal:
```bash
ros2 topic echo /chatter
```

## 5. Writing a Simple Subscriber

`simple_subscriber.py`:
```python
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class SimpleSubscriber(Node):

    def __init__(self):
        super().__init__("simple_subscriber")

        self.sub_ = self.create_subscription(String, "chatter", self.msgCallback, 10)

    def msgCallback(self, msg):
        self.get_logger().info("I heard: %s" % msg.data)


def main():
    rclpy.init()
    simple_subscriber = SimpleSubscriber()
    rclpy.spin(simple_subscriber)
    simple_subscriber.destroy_node()
    rclpy.shutdown()


if __name__ == "__main__":
    main()
```

**What it does:** listens on the same `/chatter` topic and logs every message it receives.

**Key concept:** `create_subscription(MsgType, topic_name, callback, queue_size)` — every time a message arrives on the topic, `callback` is invoked with the message as its argument.

**Pub/Sub relationship:** `simple_publisher` and `simple_subscriber` communicate purely through the `/chatter` topic — they don't know about each other directly. This is the core of ROS 2's decoupled communication model.

## 6. ROS 2 Parameters

`simple_parameter.py`:
```python
import rclpy
from rclpy.node import Node
from rcl_interfaces.msg import SetParametersResult
from rclpy.parameter import Parameter


class SimpleParameter(Node):

    def __init__(self):
        super().__init__("simple_parameter")

        self.declare_parameter("simple_int_param", 28)
        self.declare_parameter("simple_string_param", "Antonio")

        self.add_on_set_parameters_callback(self.paramChangeCallback)

    def paramChangeCallback(self, params):
        result = SetParametersResult()

        for param in params:
            if param.name == "simple_int_param" and param.type_ == Parameter.Type.INTEGER:
                self.get_logger().info("Param simple_int_param changed! New value is %d" % param.value)
                result.successful = True

            if param.name == "simple_string_param" and param.type_ == Parameter.Type.STRING:
                self.get_logger().info("Param simple_string_param changed! New value is %s" % param.value)
                result.successful = True

        return result


def main():
    rclpy.init()
    simple_parameter = SimpleParameter()
    rclpy.spin(simple_parameter)
    simple_parameter.destroy_node()
    rclpy.shutdown()


if __name__ == "__main__":
    main()
```

**What parameters are:** live-tunable configuration values a node holds (e.g. max speed, thresholds, names) — changeable without recompiling or restarting the node.

**Key concepts:**
- `declare_parameter(name, default_value)` — registers a parameter and its type/default.
- `add_on_set_parameters_callback(callback)` — hooks a function to run **every time** someone tries to change a parameter.
- The callback **must return a `SetParametersResult`** with `.successful = True/False` — ROS 2 uses this to actually approve or reject the change. This lets you validate values before they're applied (e.g. reject a negative speed).

Test it live:
```bash
ros2 param set /simple_parameter simple_int_param 42
```

**Real-world value:** this pattern allows live-tuning a running robot (e.g. adjusting `max_velocity`) without restarting anything.

## 7. `package.xml` Dependencies

Every package you `import` from directly should be declared as a dependency, e.g.:
```xml
<exec_depend>rclpy</exec_depend>
<exec_depend>std_msgs</exec_depend>
<exec_depend>rcl_interfaces</exec_depend>
```

**Lesson learned:** a typo like `<exec_depend>rcl.py</exec_depend>` (should be `rclpy`) won't break the node at runtime (Python import works because the file already exists in the environment), but it **will break `rosdep install`** on a fresh checkout of the workspace — always worth fixing for correctness.

For a robot description package, typical dependencies:
```xml
<exec_depend>robot_state_publisher</exec_depend>
<exec_depend>joint_state_publisher_gui</exec_depend>
<exec_depend>rviz2</exec_depend>
<exec_depend>ros2launch</exec_depend>
<exec_depend>gazebo_ros</exec_depend>
```

## 8. Deleting a Package Properly

To fully remove a package from a workspace:
```bash
# 1. Remove the source folder
rm -rf ~/bumperbot_ws/src/<package_name>

# 2. Clean build artifacts
cd ~/bumperbot_ws
rm -rf build/<package_name> install/<package_name> log/*<package_name>*

# 3. Rebuild
colcon build

# 4. Re-source in every open terminal (or open a new one)
source install/setup.bash

# 5. Verify it's gone
ros2 pkg list | grep <package_name>
```

**Lesson learned (why it sometimes still shows up):**
- Environment variables like `AMENT_PREFIX_PATH` **accumulate** paths every time you `source` — sourcing again doesn't remove old entries. Always test in a **fresh terminal**.
- If it's still stuck, do a full clean rebuild: `rm -rf build install log && colcon build`.

## 9. URDF & Xacro — Describing the Robot

**URDF (Unified Robot Description Format)** is XML that describes a robot's physical structure: links (rigid bodies) and joints (connections between them). **Xacro** is a macro language built on top of URDF (`.urdf.xacro` files) that adds variables, math, and file-includes to avoid repetition.

### Anatomy of a link:
```xml
<link name="base_link">
    <inertial>
        <origin xyz="0 0 0.04" rpy="0.0 0.25 0.3" />
        <mass value="8.2573504e-01"/>
        <inertia ixx="2.2124416e-02" ixy="-1.2294101e-04" ixz="3.4938785e-04"
                 iyy="2.1193702e-02" iyz="-5.0120904e-05"
                 izz="2.0064271e-02" />
    </inertial>
    <visual>
        <origin rpy="0 0 0" xyz="0 0 0"/>
        <geometry>
            <mesh filename="package://bumperbot_description/meshes/base_link.STL"/>
        </geometry>
    </visual>
    <collision>
        <origin rpy="0 0 0" xyz="0 0 0"/>
        <geometry>
            <mesh filename="package://bumperbot_description/meshes/base_link.STL"/>
        </geometry>
    </collision>
</link>
```

- **`<inertial>`** — mass and inertia tensor. **Required for Gazebo physics** (without it, Gazebo treats the link as massless, causing erratic simulation behavior). Not required just to view the robot in RViz.
- **`<visual>`** — what the link looks like (mesh, color, shape) — purely cosmetic, used by RViz/Gazebo rendering.
- **`<collision>`** — the shape used for physical contact detection. Often simplified (e.g. a `<sphere>` instead of the full mesh) for performance, since collision-checking a detailed mesh is expensive.

### Anatomy of a joint:
```xml
<joint name="wheel_right_joint" type="continuous">
    <parent link="base_link"/>
    <child link="wheel_right_link"/>
    <axis xyz="0 1 0"/>
    <origin rpy="0 0 0" xyz="0 -0.07 0"/>
</joint>
```
- `type="fixed"` — no movement (e.g. casters bolted to the base).
- `type="continuous"` — free rotation with no limits (e.g. wheels).
- `parent`/`child` define the kinematic tree — every link (except the root) has exactly one parent joint.
- `origin` — the offset/position of the child relative to the parent.

### Splitting files with `xacro:include`:
```xml
<xacro:include filename="$(find bumperbot_description)/urdf/bumperbot_gazebo.xacro"/>
```
This merges a second xacro file into the main one at build time — used to separate Gazebo-specific tags from the core geometry description, keeping files organized.

**Lesson learned:** if an included file doesn't actually exist on disk (or was never saved), you get:
```
No such file or directory: '.../urdf/bumperbot_gazebo.xacro'
```
Always verify with `ls` that every included file physically exists in `src/<pkg>/urdf/` **before** rebuilding.

## 10. CMakeLists.txt for a Description Package

```cmake
cmake_minimum_required(VERSION 3.5)
project(bumperbot_description)

find_package(ament_cmake REQUIRED)
find_package(urdf REQUIRED)

install(
  DIRECTORY launch meshes models urdf rviz
  DESTINATION share/${PROJECT_NAME}
)

if(BUILD_TESTING)
  find_package(ament_lint_auto REQUIRED)
  ament_lint_auto_find_test_dependencies()
endif()

ament_package()
```

**Key concept:** any folder not listed in `install(DIRECTORY ...)` **never makes it into `install/share/<pkg>/`**, even after a successful build. This caused a real error:
```
file 'display.launch.py' was not found in the share directory of package 'bumperbot_description'
```
— fixed by adding `launch` (and later `rviz`, `models`) to the `install()` directory list.

## 11. Visualizing with RViz

Manual 3-terminal workflow (before launch files):

**Terminal 1 — publishes `/tf` from joint states:**
```bash
ros2 run robot_state_publisher robot_state_publisher --ros-args \
  -p robot_description:="$(xacro ~/bumperbot_ws/src/bumperbot_description/urdf/bumperbot.urdf.xacro)"
```

**Terminal 2 — fake joint angle source (sliders GUI):**
```bash
ros2 run joint_state_publisher_gui joint_state_publisher_gui
```

**Terminal 3 — 3D visualizer:**
```bash
ros2 run rviz2 rviz2
```

**Data flow:**
```
joint_state_publisher_gui --publishes--> /joint_states
                                              |
                                              v
                                robot_state_publisher (subscribes)
                                              |
                                (publishes) /tf, /tf_static
                                              |
                                              v
                                          rviz2 (subscribes, visualizes)
```

**Lesson learned:** always use `~` or `get_package_share_directory()` for paths instead of hardcoding `/home/<username>/...` — a path copied from another machine/tutorial (e.g. `/home/alien/...`) will fail with `FileNotFoundError` on a different username.

### `rviz/display.rviz`
A **saved RViz configuration** (which displays are enabled — Grid, TF, RobotModel — camera angle, panels, etc.), so it doesn't need to be manually reconfigured every time RViz opens. Loaded via:
```bash
ros2 run rviz2 rviz2 -d <path_to_display.rviz>
```

## 12. Launch Files (`display.launch.py`)

Automates all three RViz terminals into a single command:

```python
import os
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue
from launch.substitutions import Command, LaunchConfiguration
from ament_index_python.packages import get_package_share_directory


def generate_launch_description():

    model_arg = DeclareLaunchArgument(
        name="model",
        default_value=os.path.join(get_package_share_directory("bumperbot_description"), "urdf", "bumperbot.urdf.xacro"),
        description="Absolute path to robot URDF file"
    )

    robot_description = ParameterValue(Command(["xacro ", LaunchConfiguration("model")]), value_type=str)

    robot_state_publisher = Node(
        package="robot_state_publisher",
        executable="robot_state_publisher",
        parameters=[{"robot_description": robot_description}]
    )

    joint_state_publisher_gui = Node(
        package="joint_state_publisher_gui",
        executable="joint_state_publisher_gui"
    )

    rviz_node = Node(
        package="rviz2",
        executable="rviz2",
        name="rviz2",
        output="screen",
        arguments=["-d", os.path.join(get_package_share_directory("bumperbot_description"), "rviz", "display.rviz")]
    )

    return LaunchDescription([
        model_arg,
        robot_state_publisher,
        joint_state_publisher_gui,
        rviz_node
    ])
```

Run with:
```bash
ros2 launch bumperbot_description display.launch.py
```

**Key concepts:**
- `get_package_share_directory("<pkg>")` dynamically resolves the install path — no hardcoded usernames, works on any machine.
- `DeclareLaunchArgument` + `LaunchConfiguration` lets someone override the `model` path from the command line if needed, while defaulting sensibly.
- `Node(...)` actions replace individual `ros2 run` commands — one per node.
- `LaunchDescription([...])` bundles everything to start together.

## 13. Adding Physics for Gazebo (`bumperbot_gazebo.xacro`)

Gazebo needs extra physics tags per-link that RViz doesn't care about — friction, contact stiffness/damping:

```xml
<?xml version="1.0"?>
<robot name="bumperbot" xmlns:xacro="http://www.ros.org/wiki/xacro">

    <gazebo reference="wheel_right_link">
        <mu1>100000000000000.0</mu1>
        <mu2>100000000000000.0</mu2>
        <kp>1000000000000.0</kp>
        <kd>10.0</kd>
        <minDepth>0.001</minDepth>
        <maxVel>0.1</maxVel>
        <fdir1>1 0 0</fdir1>
    </gazebo>

    <gazebo reference="wheel_left_link">
        <mu1>100000000000000.0</mu1>
        <mu2>100000000000000.0</mu2>
        <kp>1000000000000.0</kp>
        <kd>10.0</kd>
        <minDepth>0.001</minDepth>
        <maxVel>0.1</maxVel>
        <fdir1>1 0 0</fdir1>
    </gazebo>

    <gazebo reference="caster_front_link">
        <mu1>0.1</mu1>
        <mu2>0.1</mu2>
        <kp>1000000.0</kp>
        <kd>100.0</kd>
        <minDepth>0.001</minDepth>
        <maxVel>0.1</maxVel>
    </gazebo>

    <gazebo reference="caster_rear_link">
        <mu1>0.1</mu1>
        <mu2>0.1</mu2>
        <kp>1000000.0</kp>
        <kd>100.0</kd>
        <minDepth>0.001</minDepth>
        <maxVel>0.1</maxVel>
    </gazebo>

</robot>
```

**Why the values differ:**
- **Wheels** have extremely high friction (`mu1`/`mu2` ≈ `1e14`) so they grip the ground and don't slip — needed for accurate differential-drive motion.
- **Casters** have low friction (`0.1`) so they roll/pivot freely, mimicking real swivel casters.
- `kp`/`kd` control contact stiffness/damping (how "hard" or "springy" a collision feels to the physics engine).

Included into the main URDF with:
```xml
<xacro:include filename="$(find bumperbot_description)/urdf/bumperbot_gazebo.xacro"/>
```

## 14. Simulating in Gazebo (`gazebo.launch.py`)

```python
import os
from os import pathsep
from ament_index_python.packages import get_package_share_directory, get_package_prefix

from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument, SetEnvironmentVariable, IncludeLaunchDescription
from launch.substitutions import Command, LaunchConfiguration
from launch.launch_description_sources import PythonLaunchDescriptionSource

from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue


def generate_launch_description():

    bumperbot_description = get_package_share_directory("bumperbot_description")
    bumperbot_description_prefix = get_package_prefix("bumperbot_description")

    model_path = os.path.join(bumperbot_description, "models")
    model_path += pathsep + os.path.join(bumperbot_description_prefix, "share")

    env_variable = SetEnvironmentVariable("GAZEBO_MODEL_PATH", model_path)

    model_arg = DeclareLaunchArgument(name="model", default_value=os.path.join(
                                        bumperbot_description, "urdf", "bumperbot.urdf.xacro"
                                        ),
                                       description="Absolute path to robot urdf file")

    robot_description = ParameterValue(Command(["xacro ", LaunchConfiguration("model")]),
                                        value_type=str)

    robot_state_publisher_node = Node(
        package="robot_state_publisher",
        executable="robot_state_publisher",
        parameters=[{"robot_description": robot_description}]
    )

    start_gazebo_server = IncludeLaunchDescription(PythonLaunchDescriptionSource(os.path.join(
        get_package_share_directory("gazebo_ros"), "launch", "gzserver.launch.py"
    )))

    start_gazebo_client = IncludeLaunchDescription(PythonLaunchDescriptionSource(os.path.join(
        get_package_share_directory("gazebo_ros"), "launch", "gzclient.launch.py"
    )))

    spawn_robot = Node(
        package="gazebo_ros",
        executable="spawn_entity.py",
        arguments=["-entity", "bumperbot", "-topic", "robot_description"],
        output="screen"
    )

    return LaunchDescription([
        env_variable,
        model_arg,
        robot_state_publisher_node,
        start_gazebo_server,
        start_gazebo_client,
        spawn_robot
    ])
```

Run with:
```bash
ros2 launch bumperbot_description gazebo.launch.py
```

**Key concepts:**
- `SetEnvironmentVariable("GAZEBO_MODEL_PATH", ...)` tells Gazebo where to find custom model/mesh folders.
- `IncludeLaunchDescription` reuses Gazebo's **own** launch files (`gzserver.launch.py`, `gzclient.launch.py`) instead of reimplementing Gazebo startup logic — `gzserver` runs the physics simulation, `gzclient` runs the GUI.
- `spawn_entity.py` (from `gazebo_ros`) injects the robot into the running simulation by reading the `robot_description` topic/parameter published by `robot_state_publisher_node`.

**Dependency reminder:** requires `gazebo_ros` declared in `package.xml`:
```xml
<exec_depend>gazebo_ros</exec_depend>
```

## 15. Common Errors & Fixes (Debug Log)

| Error | Root Cause | Fix |
|---|---|---|
| `invalid choice: 'create--'` | Missing space before `--build-type` | `ros2 pkg create --build-type ...` |
| `error: the following arguments are required: executable_name` | Ran `ros2 run <pkg>` with no executable name | `ros2 run <pkg> <executable>` |
| `ModuleNotFoundError: No module named 'bumpebot_py_examples'` | `setup.py` entry point module name didn't match actual folder name (typo) | Match `entry_points` string exactly to the real inner package folder name |
| `colcon build` succeeds but new entry point still missing | `setup.py` had unsaved changes in the editor | Save the file (`Ctrl+S`) before building |
| Package still shows in `ros2 pkg list` after deletion | Stale `AMENT_PREFIX_PATH` from repeated sourcing in the same terminal | Open a fresh terminal; full clean rebuild (`rm -rf build install log`) |
| `FileNotFoundError` on xacro path | Hardcoded path from another machine/username (e.g. `/home/alien/...`) | Use `~` or `get_package_share_directory()` instead of hardcoded paths |
| `file 'display.launch.py' was not found in the share directory` | `CMakeLists.txt` didn't install the `launch` folder | Add `launch` (and `rviz`, `models`) to `install(DIRECTORY ...)` |
| `No such file or directory: '.../bumperbot_gazebo.xacro'` | Included xacro file was referenced but never actually saved to disk | Create and save the missing file in `src/<pkg>/urdf/`, then rebuild |
| `radisu="0.033"` accepted silently, collision missing | Typo: `radisu` instead of `radius` | Always double-check attribute spelling in URDF/xacro |

## General Workflow Checklist (any time something doesn't work)

1. Does the file actually exist where it's expected? (`ls`/`find`)
2. Was the file **saved** before building? (check for unsaved-dot in editor tab)
3. Did you run `colcon build` **after** the last change?
4. Did you re-`source install/setup.bash` in the terminal you're testing in?
5. Is the path hardcoded to a different username/machine?
6. Is the folder actually listed in `CMakeLists.txt`'s `install(DIRECTORY ...)`?
7. Are all used packages declared in `package.xml`?
8. Try a fresh terminal — stale environment variables cause confusing "ghost" behavior.
